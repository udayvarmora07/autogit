# Phase 1 P1-01 through P1-05 implementation evidence

Date: 2026-09-07  
Commit under review: working tree after `6e9113e`  
Reviewer: pending native-platform review

This bundle records the local implementation evidence for the first five
Phase 1 work packages. It does not promote the Phase 1 or private-alpha gate:
native macOS/Windows runtime evidence, Landlock/namespace/AppContainer
isolation, and the remaining Phase 1 work are still required.

## P1-01 — SQLite durability contract

- `internal/db` now asserts SQLite version, WAL journal mode, synchronous mode,
  foreign keys, busy timeout, WAL auto-checkpoint, and local-filesystem policy
  on writable opens.
- Linux rejects known network/user-space filesystem types; macOS rejects known
  network filesystem types; Windows and other platforms retain an explicit
  conservative fallback until native filesystem detection is available.
- Read-only inspection reports the live contract without creating or migrating
  state.
- `internal/db/database_test.go` and `internal/db/maintenance_test.go` cover
  the runtime contract, restrictive files, read-only behavior, and unsafe
  artifacts.

## P1-02 — Backup, restore, integrity, repair, and export

- `db.Backup` uses checkpointed `VACUUM INTO`, validates the standalone result,
  and publishes it atomically without overwriting an existing destination.
- `db.Restore` validates the backup, copies it through a synced temporary file,
  removes only validated stale WAL/SHM sidecars, and atomically replaces the
  requested state database. Restoring a prior backup is the supported
  migration rollback mechanism; no destructive in-place schema downgrade is
  attempted.
- `db.Inspect` runs integrity and foreign-key checks; `db.Repair` performs only
  checkpoint/optimization after a healthy open; `db.Export` emits structural
  table counts and health facts without payloads or metadata.
- CLI surfaces are available as `backup --output`, `restore --input`,
  `integrity`, `repair`, and `export`.

## P1-03 — Bounded retention and compaction

- `db.Retain` supports age/row-bounded audit-event pruning, published-outbox
  pruning, expired-lease cleanup, audit-chain compaction, and explicit VACUUM.
- Pending events, pending outbox effects, and active leases are preserved.
- Old receipt rows move to payload-free tombstones so replay remains an
  idempotency/conflict check after hot-table compaction; event logs join both
  active receipts and tombstones.
- Retention and redacted-export tests prove pending recovery state survives and
  secret-like metadata is not emitted.

## P1-04 — Verifier isolation capability baseline

- `verification.IsolationTier` defines none, process-bounded,
  filesystem-isolated, filesystem-and-network-isolated, and remote-hermetic
  tiers.
- Process-bounded execution is the default and records the achieved tier in
  digest-bound evidence. It uses direct argv, scrubbed environment, bounded
  output, timeouts, descendant cleanup, and OS resource ceilings where the
  platform exposes them (Linux `prlimit`; existing Windows job-tree and macOS
  process-group boundaries remain explicit).
- The original P1-04 baseline recorded stronger tiers as unavailable. The
  current Linux implementation now enforces filesystem and filesystem/network
  tiers with bubblewrap namespaces and explicit read-only allowlists; its
  machine-readable capability report probes Landlock but explicitly does not
  claim an in-process Landlock ruleset. Windows reports job-object controls
  without claiming AppContainer, and macOS reports its process-group fallback.
  See the follow-up [P1-06–P1-10 evidence bundle](phase-1-p1-06-p1-10.md).
  Platforms without the native namespace boundary still fail closed, and
  public verification cannot select the `none` tier.
- The native portability test for the process-bounded tier asserts the
  platform-specific primitive that the implementation reports: Linux
  `process-group+prlimit`, macOS `process-group`, and Windows `job-object`.
  This keeps platform fallback evidence honest instead of applying a Linux-only
  expectation to every runner.

## P1-05 — Pinned offline secret scanning

- `security.OfflineSecretScanner` and `PinnedOfflineScanner` provide a pinned
  `autogit-secret-scanner/v1` boundary over immutable exact candidate blobs.
- Reports include scanner version, files presented/scanned, bytes scanned,
  truncation/limit state, redacted finding fingerprints, fixed provider
  push-protection guidance, redacted summary, and a digest that excludes
  source values.
- Candidate publication preflight and exact-SHA history scanning use the
  pinned interface. History evidence records the scanner identity and
  coverage counters. No online/provider scanner is implicitly invoked.
